Creating a Release

Guide for Release Managers of Apache Paimon Mosaic, following ASF Release Policy.

Overview

The release process consists of:

  1. Decide to release
  2. Prepare for the release
  3. Build a release candidate
  4. Vote on the release candidate
  5. If necessary, fix any issues and go back to step 3
  6. Finalize the release
  7. Promote the release

Automated Publishing

When a version tag is pushed, the Release workflow orchestrates language-specific release jobs:

ComponentTag PatternPublished ToPre-release (-rc) BehaviorOrdering
Rust cratev0.1.0crates.ioDry-run onlyFinal publication starts only after Java and all wheel jobs succeed
Java bindingv0.1.0-rc1Apache Nexus staging (Release Manager)CI verifies and exports the native inputs; the Release Manager signs and stages locallyFinal tags verify the artifacts but do not create a second staging repository
Python bindingv0.1.0PyPIPublishes a unique RC version to TestPyPIFinal PyPI publication follows successful Rust publication

Only the top-level Release workflow authorizes automated registry publication. Manually dispatching a leaf workflow is a safe build/dry-run and cannot bypass the top-level preflight. Java signing and Nexus staging are never authorized to CI and remain explicit Release Manager operations.

The Release Manager is responsible for the source release (tarball + signature), local Java signing and Nexus staging, and coordination of the community vote. CI handles Rust and Python publication only after their release gates pass.

Decide to Release

Anybody can propose a release on the dev mailing list, giving a short rationale and nominating a committer as Release Manager (including themselves).

Checklist:

  • Community agrees to release
  • A Release Manager is selected

Prepare for the Release

One-time Release Manager Setup

GPG Key

  1. Install GnuPG:

    # macOS
brew install gnupg

# Ubuntu / Debian
sudo apt install gnupg2

  2. Generate a key pair (RSA 4096, does not expire, use your @apache.org email):

    gpg --full-gen-key

  3. Find your key ID:

    gpg --list-keys --keyid-format short

  4. Upload to key server:

    gpg --keyserver hkps://keyserver.ubuntu.com --send-keys <YOUR_KEY_ID>

  5. Append to the project KEYS file:

    svn co https://dist.apache.org/repos/dist/release/paimon/ paimon-dist-release --depth=files
cd paimon-dist-release
(gpg --list-sigs <YOUR_KEY_ID> && gpg --armor --export <YOUR_KEY_ID>) >> KEYS
svn ci -m "Add <YOUR_NAME>'s public key"

  6. Configure Git to sign tags:

    git config --global user.signingkey <YOUR_KEY_ID>

GitHub Actions Publication Secrets

Ensure the following repository secrets are configured:

SecretPurpose
CARGO_REGISTRY_TOKENcrates.io publishing
PYPI_API_TOKENPyPI publishing
TEST_PYPI_API_TOKENTestPyPI publishing

Do not upload a release manager's personal GPG private key or Nexus credentials to GitHub Actions. Java artifacts are signed and staged from a trusted local machine after downloading the verified native inputs from the exact RC workflow run.

Clone into a Fresh Workspace

git clone https://github.com/apache/paimon-mosaic.git
cd paimon-mosaic

The release automation requires Python 3.11+ because its lockfile and license tools use tomllib. The published paimon-mosaic Python package itself continues to support Python 3.9+.

Set Up Environment Variables

RELEASE_VERSION="0.1.0"
SHORT_RELEASE_VERSION="0.1"
NEXT_VERSION="0.2.0"
RC_NUM="1"
RELEASE_BRANCH="release-${SHORT_RELEASE_VERSION}"
RC_TAG="v${RELEASE_VERSION}-rc${RC_NUM}"
RELEASE_TAG="v${RELEASE_VERSION}"

Generate Dependency License Manifests

ASF releases must include a declaration of third-party dependency licenses. Generate and commit dependency manifests on main before creating the release branch, so the release branch and source archive contain the same reviewed manifests.

# Install the pinned release tooling (one-time)
cargo install cargo-deny --version 0.19.0 --locked
cargo install cargo-about --version 0.9.1 --locked

git checkout main
git pull --ff-only origin main

# Refresh all lockfile-derived legal metadata
cargo fetch --locked
python3 tools/dependencies.py generate
python3 tools/generate_license_reports.py

# Verify licenses and report freshness
python3 tools/dependencies.py check
python3 tools/generate_license_reports.py --check

git add Cargo.lock DEPENDENCIES.rust.tsv core/DEPENDENCIES.rust.tsv ffi/DEPENDENCIES.rust.tsv jni/DEPENDENCIES.rust.tsv cli/DEPENDENCIES.rust.tsv java/src/main/binary-resources python/licenses
git commit -m "chore: update dependency list for release ${RELEASE_VERSION}"
git push origin main

Fix any license violations before proceeding. The generated files must be committed before tagging because create_source_release.sh builds the archive from the committed Git tree.

Create a Release Branch

Create one stable release branch for the release line. Do not include the RC number in the branch name; RC attempts are represented by tags such as v0.1.0-rc1 and v0.1.0-rc2.

git checkout main
git pull --ff-only origin main
git checkout -b ${RELEASE_BRANCH}
git push origin ${RELEASE_BRANCH}

Bump Version on Main

After cutting the release branch, bump main to the next development version:

git checkout main
git pull --ff-only origin main
cd tools
OLD_VERSION=${RELEASE_VERSION} NEW_VERSION=${NEXT_VERSION}-SNAPSHOT ./update_branch_version.sh
cd ..
git push origin main

The script updates version strings in all pom.xml (matching both ${OLD_VERSION} and ${OLD_VERSION}-SNAPSHOT), Cargo.toml (excluding target/), and python/pyproject.toml files. It also refreshes Cargo.lock, dependency manifests, and generated binary legal reports before creating the commit.

Build a Release Candidate

Update Versions on the Release Branch

Before tagging, update the release branch to non-SNAPSHOT versions (removing -SNAPSHOT from pom.xml):

git checkout ${RELEASE_BRANCH}
git pull --ff-only origin ${RELEASE_BRANCH}
cd tools
OLD_VERSION=${RELEASE_VERSION}-SNAPSHOT NEW_VERSION=${RELEASE_VERSION} ./update_branch_version.sh
cd ..

This ensures the Java artifacts staged for the RC carry the final release version (e.g. 0.1.0) rather than a SNAPSHOT suffix. The release workflows and source packaging script independently reject a tag whose Java, Rust, Python, or lockfile versions do not match.

Create the RC Tag

Push a signed RC tag to trigger CI workflows:

git tag -s ${RC_TAG} -m "${RC_TAG}"
git tag -v ${RC_TAG}
git push origin ${RELEASE_BRANCH}
git push origin ${RC_TAG}

The tag must use the canonical vX.Y.Z-rcN form and its OpenPGP signer must be present in the Apache Paimon KEYS file. Every RC number maps to a distinct TestPyPI version; if that version already exists, create a new RC tag instead of overwriting or skipping files.

After pushing, verify in GitHub Actions that the Release workflow succeeds:

  • Release preflight — runs license, advisory, formatting, Clippy, Rust, C++, Java, Python, and artifact checks before any staging or publication job starts
  • Rust release — dry-run check (does not publish for RC tags)
  • Java release — builds native JNI libraries for 4 platforms, verifies the combined JARs, and uploads one java-release-native-inputs artifact for the release manager
  • Python wheels — builds wheels for 4 platforms
  • Python publish — publishes to TestPyPI only after the Rust, Java, and Python wheel jobs succeed

The PyPI flow intentionally publishes binary wheels only. The signed ASF source archive is the authoritative source release; do not upload a Python sdist that lacks a target native library.

If only the Python publish job fails due to a transient PyPI or TestPyPI issue, use Re-run failed jobs on the Release workflow. The successful Rust, Java, and Python wheel jobs do not need to be repeated.

Sign and Stage Java Artifacts Locally

Use the exact successful Release workflow run for the RC tag. Confirm that the run's head SHA is the signed RC commit, then download its already verified four-platform native input bundle:

RELEASE_RUN_ID="<successful Release workflow run ID>"
RC_COMMIT_SHA="$(git rev-parse "${RC_TAG}^{commit}")"

test "$(gh run view "${RELEASE_RUN_ID}" \
  --repo apache/paimon-mosaic --json headSha --jq .headSha)" = "${RC_COMMIT_SHA}"
test "$(gh run view "${RELEASE_RUN_ID}" \
  --repo apache/paimon-mosaic --json conclusion --jq .conclusion)" = "success"
test "$(gh run view "${RELEASE_RUN_ID}" \
  --repo apache/paimon-mosaic --json workflowName --jq .workflowName)" = "Release"
test "$(gh run view "${RELEASE_RUN_ID}" \
  --repo apache/paimon-mosaic --json event --jq .event)" = "push"
test "$(gh run view "${RELEASE_RUN_ID}" \
  --repo apache/paimon-mosaic --json headBranch --jq .headBranch)" = "${RC_TAG}"

git checkout --detach "${RC_TAG}"
mkdir -p java/src/main/resources/native
gh run download "${RELEASE_RUN_ID}" \
  --repo apache/paimon-mosaic \
  --name java-release-native-inputs \
  --dir java/src/main/resources/native
find java/src/main/resources/native -type f | sort

Build and verify the unsigned JARs before signing. The verifier requires all four native libraries and artifact-exact legal metadata:

mvn -f java/pom.xml clean verify -Prelease -Dgpg.skip=true -DskipTests

MAIN_JAR="$(find java/target -maxdepth 1 -name 'mosaic-*.jar' \
  ! -name '*-sources.jar' ! -name '*-javadoc.jar' -print -quit)"
SOURCES_JAR="$(find java/target -maxdepth 1 -name '*-sources.jar' -print -quit)"
JAVADOC_JAR="$(find java/target -maxdepth 1 -name '*-javadoc.jar' -print -quit)"
python3 tools/verify_java_jars.py \
  --main "${MAIN_JAR}" \
  --sources "${SOURCES_JAR}" \
  --javadoc "${JAVADOC_JAR}" \
  --require-all-natives

Keep the personal signing key on this trusted machine. Run signing and deployment in a strict subshell so the short-lived GPG passphrase and Nexus credentials disappear on both success and failure, while any Maven failure remains visible to the caller:

(
  set -euo pipefail
  export NEXUS_STAGE_DEPLOYER_USER="<ASF Nexus username>"
  read -rsp "Nexus password: " NEXUS_STAGE_DEPLOYER_PW; echo
  read -rsp "GPG passphrase: " MAVEN_GPG_PASSPHRASE; echo
  export NEXUS_STAGE_DEPLOYER_PW MAVEN_GPG_PASSPHRASE

  cd java
  mvn deploy \
    --settings ../deploysettings.xml \
    -Prelease \
    -DskipTests \
    -Dgpg.keyname="<FULL_GPG_FINGERPRINT>" \
    -DstagingDescription="Apache Paimon Mosaic ${RELEASE_VERSION} RC${RC_NUM}"
)

Record the closed orgapachepaimon-XXXX repository URL and verify its artifacts before including it in the vote email. If local signing, deployment, or verification fails, drop that staging repository and do not start the vote.

Create Source Release Artifacts

Create source release artifacts from the same commit as the RC tag:

git checkout ${RC_TAG}
cd tools
RELEASE_VERSION=${RELEASE_VERSION} ./create_source_release.sh

This creates the following under tools/release/:

  • apache-paimon-mosaic-${RELEASE_VERSION}-src.tgz — source archive
  • apache-paimon-mosaic-${RELEASE_VERSION}-src.tgz.asc — GPG signature
  • apache-paimon-mosaic-${RELEASE_VERSION}-src.tgz.sha512 — SHA-512 checksum

Stage Artifacts to SVN

SOURCE_REPO="$(git rev-parse --show-toplevel)"
DIST_DEV_DIR="$(dirname "${SOURCE_REPO}")/paimon-dist-dev"
svn checkout https://dist.apache.org/repos/dist/dev/paimon/ \
  "${DIST_DEV_DIR}" --depth=immediates
cd "${DIST_DEV_DIR}"
mkdir paimon-mosaic-${RELEASE_VERSION}-rc${RC_NUM}
cp "${SOURCE_REPO}"/tools/release/apache-paimon-mosaic-${RELEASE_VERSION}-src.* \
   paimon-mosaic-${RELEASE_VERSION}-rc${RC_NUM}/
svn add paimon-mosaic-${RELEASE_VERSION}-rc${RC_NUM}
svn commit -m "Add paimon-mosaic ${RELEASE_VERSION} RC${RC_NUM}"

Checklist:

  • RC tag pushed and the CI release workflow succeeded
  • Source tarball, signature, and checksum staged to dist.apache.org dev
  • Java artifacts are present in a closed Nexus staging repository
  • Python wheels published to TestPyPI

Vote on the Release Candidate

Start a vote on the dev mailing list.

Subject: [VOTE] Release Apache Paimon Mosaic ${RELEASE_VERSION} (RC${RC_NUM})

Hi everyone,

Please review and vote on release candidate #${RC_NUM} for Apache Paimon Mosaic ${RELEASE_VERSION}.

[ ] +1 Approve the release
[ ] +0 No opinion
[ ] -1 Do not approve (please provide specific comments)

The release candidate is available at:
https://dist.apache.org/repos/dist/dev/paimon/paimon-mosaic-${RELEASE_VERSION}-rc${RC_NUM}/

Git tag:
https://github.com/apache/paimon-mosaic/releases/tag/${RC_TAG}

Git commit:
<RC_COMMIT_SHA>

Exact successful GitHub Actions Release run:
https://github.com/apache/paimon-mosaic/actions/runs/<RELEASE_RUN_ID>

KEYS for signature verification:
https://downloads.apache.org/paimon/KEYS

Java artifacts (Nexus staging):
https://repository.apache.org/content/repositories/orgapachepaimon-XXXX/

Python wheels (TestPyPI):
https://test.pypi.org/project/paimon-mosaic/${RELEASE_VERSION}rc${RC_NUM}/

The vote passes only after at least 72 hours, with at least three binding +1 votes from PMC members and more binding +1 than binding -1 votes. After it passes, send a result email with subject [RESULT][VOTE] Release Apache Paimon Mosaic ${RELEASE_VERSION} (RC${RC_NUM}) and summarize the named votes and vote thread:

- <PMC member name>

- <name or none>

- <name or none>

Non-binding votes:
- <vote and name, or none>

Vote thread:
<mailing-list archive URL>

Fix Any Issues

If the vote reveals issues:

  1. Fix them on the release branch via normal PRs.
  2. Remove the old RC from dist dev (optional): 
    cd paimon-dist-dev
svn remove paimon-mosaic-${RELEASE_VERSION}-rc${RC_NUM}
svn commit -m "Remove paimon-mosaic ${RELEASE_VERSION} RC${RC_NUM} (superseded)"
  3. Drop the Nexus staging repository via the Nexus UI.
  4. Increment RC_NUM, then go back to Build a release candidate.

Finalize the Release

Move Source Artifacts to the Release Repository

After the vote passes, promote the approved source candidate to the ASF release area before pushing the final tag. The final publication workflow refuses to publish crates or wheels until the archive, signature, and checksum are available from downloads.apache.org and pass checksum and signature verification.

svn mv -m "Release paimon-mosaic ${RELEASE_VERSION}" \
  https://dist.apache.org/repos/dist/dev/paimon/paimon-mosaic-${RELEASE_VERSION}-rc${RC_NUM} \
  https://dist.apache.org/repos/dist/release/paimon/paimon-mosaic-${RELEASE_VERSION}

for suffix in "" ".asc" ".sha512"; do
  curl --fail --location --silent --show-error \
    --output /dev/null \
    "https://downloads.apache.org/paimon/paimon-mosaic-${RELEASE_VERSION}/apache-paimon-mosaic-${RELEASE_VERSION}-src.tgz${suffix}"
done

Push the Release Tag

Once the vote passes, create the final release tag on the exact approved RC commit. The final and RC tags must both be signed by a key in the Apache Paimon KEYS file. CI rejects a final tag that does not match at least one signed vX.Y.Z-rcN tag.

git fetch origin ${RC_TAG}
git checkout --detach ${RC_TAG}
test "$(git rev-parse HEAD)" = "$(git rev-parse ${RC_TAG}^{commit})"
git tag -s ${RELEASE_TAG} -m "Release Apache Paimon Mosaic ${RELEASE_VERSION}"
git tag -v ${RELEASE_TAG}
git push origin ${RELEASE_TAG}

The final workflow completes the full preflight, Java verification, and target-runner wheel build/import checks. It verifies the promoted ASF source release and confirms that the crates.io and PyPI versions are absent, publishes the Rust crate, and finally publishes the wheels to PyPI. It does not deploy or release Java artifacts from the final tag.

Release the Java Artifacts

  1. Go to Apache Nexus Staging Repositories.
  2. Find the closed orgapachepaimon-XXXX repository created by the trusted local RC staging step.
  3. Confirm its description and contents still identify the approved RC.
  4. Click Release to promote it to Maven Central; do not create or close a second repository from the final tag.

Verify Published Artifacts

  • Rust: crates.io/crates/paimon-mosaic-core shows version ${RELEASE_VERSION}
  • Java: Maven Central shows version ${RELEASE_VERSION}
  • Python: PyPI — paimon-mosaic shows version ${RELEASE_VERSION}

Create GitHub Release

  1. Go to Releases — New release.
  2. Choose tag v${RELEASE_VERSION}.
  3. Click Generate release notes and review.
  4. Click Publish release.

Checklist:

  • Source artifacts moved to dist release
  • Release tag pushed; CI published to crates.io and PyPI
  • Java artifacts released to Maven Central via Nexus
  • GitHub Release created

Promote the Release

Update the Releases Page

Update the Releases page: move the released version from "Upcoming" to "Past Releases" with a summary of key features and a link to the GitHub release notes.

Announce the Release

Wait at least 24 hours after finalizing. Send the announcement to dev@paimon.apache.org and announce@apache.org using your @apache.org email in plain text.

Subject: [ANNOUNCE] Release Apache Paimon Mosaic ${RELEASE_VERSION}

The Apache Paimon community is pleased to announce the release of
Apache Paimon Mosaic ${RELEASE_VERSION}.

Apache Paimon Mosaic is a columnar-bucket hybrid format optimized for
wide tables of Apache Paimon.

Rust:   cargo add paimon-mosaic-core
Java:   <dependency>
          <groupId>org.apache.paimon</groupId>
          <artifactId>mosaic</artifactId>
          <version>${RELEASE_VERSION}</version>
        </dependency>
Python: pip install paimon-mosaic

Downloads:
https://paimon.apache.org/docs/mosaic/releases.html

Release notes:
https://github.com/apache/paimon-mosaic/releases/tag/v${RELEASE_VERSION}

Thanks to all contributors!

Clean Up Old Releases

ASF policy requires only the latest release in the dist release area. Remove older versions:

svn rm -m "Remove old release" \
  https://dist.apache.org/repos/dist/release/paimon/paimon-mosaic-${OLD_VERSION}
